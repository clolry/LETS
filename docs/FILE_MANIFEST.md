## Finding M-2 — the real two-data-layer problem is inside `lets_app/`

There are two incompatible data layers, but both live in `lets_app/server/` and neither is the `LETS_SYSTEM_*` schema:

| | Layer A — TRIP inheritance | Layer B — LETS additions |
|---|---|---|
| Defined in | `lets_app/server/01_constants/Sheets.js` (`SHEET_NAMES`, `TRAVEL_SHEET_SCHEMAS`) | `lets_app/server/00_config/BudgetConfig.js` (`LETS_CONFIG.sheets`) + `lets_app/server/20_data/LetsDB.js` (`SCHEMAS`) |
| Accessed through | `lets_app/server/20_data/TravelDB.js` (class `TravelDB`) | `LetsDB` factory object |
| Tabs declared | 16 | 7 |
| Column naming | `Request_ID`, `Trip_Name` — underscore-separated | `RequestID`, `EventName` — camel/Pascal, no separator |
| Reachable from a running web app today | **Yes** — every one of the 63 client-callable functions goes here | **No** — zero references from any entry point (see Finding M-3) |

**Tab-name collision: `Requests`.** Both layers declare a tab literally named `Requests`, with mutually incompatible column sets. `TRAVEL_SHEET_SCHEMAS.Requests` declares 42 columns beginning `Request_ID, Status, Trip_Name`. `LetsDB.SCHEMAS['Requests']` declares 20 columns beginning `RequestID, Status, EventName`. `[VERIFIED]` `lets_app/server/01_constants/Sheets.js:57-100` vs `lets_app/server/20_data/LetsDB.js:84-105`. Consequence is analyzed in the data dictionary; the short version is that `LetsDB.initializeDatabase()` checks only `getLastRow() === 0` before writing its own header row, so pointing it at the live TRIP database would either skip silently (populated sheet) or overwrite headers (empty sheet).
